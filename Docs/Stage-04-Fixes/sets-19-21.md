## S19 — Barcode: generation API & label printing

One feature end to end: a backend generator, its use in the product forms, and printing labels from the products list.

### Generation API *(contract → backend → frontend)*

- **Format:** the first two letters of the product's **family**, uppercased, then the first two letters of its **brand**, uppercased, then **5 random digits**. Family "display" with brand "iphone" yields `DIIP00001`. Digits are zero-padded to exactly five characters.
- **Uniqueness:** before returning, the service checks the candidate against the database; on collision it regenerates **only the five digits** and re-checks. The plan must specify a **bounded retry count** and the error returned when the bound is exhausted (see decision **Q2**).
- **Contract:** add the route constant, the command (family id and brand id) and the response DTO to the catalog module. No magic strings — the retry bound, the digit count and the letter count are named constants.
- **Backend:** route → controller → service in the catalog module, following the module's existing 6-file structure. The letter extraction must handle names shorter than two letters, accents, and non-Latin characters — see decision **Q1**.
- **Frontend:** a service and hook pair following the catalog module's existing pattern; the hook is a **mutation**, not a query (each call must produce a fresh value, never a cached one).

### Product forms — Add Product and Product Info

- The barcode field gains an **auto-generate button**. The field remains **freely editable**: a generated barcode is a suggestion, never mandatory, and the user may type their own or clear it.
- Clicking generate when **family or brand is not yet selected** shows a toast asking the user to select a family and brand first, and makes no request.
- **Product Info:** the same button in edit mode. Note that S3 of the existing programme leaves barcode editing disabled on the Add Product page — this set **supersedes that**: the field is editable on both pages.
- Barcode uniqueness is enforced by the database. If a save fails on that constraint, the error must land **on the barcode field**, not in a generic banner.

### Products list — print labels

- Beside the edit action, add a **print-barcode button**. It opens a dialog with a **quantity input defaulting to the product's current stock quantity**, and a print action.
- The dialog renders that many barcode labels and opens the browser's print view. The label shows the barcode symbol plus its human-readable value; the plan should state whether the product name is included (decision **Q4**).
- **Symbology: Code 128** — the format is alphanumeric and nine characters, so EAN-13 and UPC are not applicable. The plan names the rendering library and confirms it is already a dependency or must be added.
- A product with **no barcode** must not offer the action (or must offer it disabled with an explanation).

## S20 — Storefront products page: align to the admin/staff pattern *(frontend only)*

The public products page was built before the admin and staff product pages and does not follow their structure. Refactor — or rebuild — it so its **logic** matches theirs: the same filter-state handling, the same service and hook layering, the same query-key and pagination conventions, the same loading, empty and error handling.

**The UI does not change.** This is a structural refactor; the page must look and behave the same to a visitor afterwards, aside from the bug fixes below that fall out of the alignment.

The planning agent must **read the admin and staff products pages first** and describe their pattern explicitly — filter state shape, where the debounce lives, how filters map to query parameters and to the URL, how the query key is composed, how pagination is driven — then apply that pattern to the storefront page.

**Constraints that must survive the refactor** (the storefront is not simply a permissioned admin page):

- Only **published and enabled** products are listed; the public list never exposes cost, exact stock quantities, reserved quantities or margins.
- **Price visibility rules stay intact:** a guest sees the guest price or the "registered users only" state; an approved client sees his category price. Price resolution is the backend's job and must not migrate into the frontend during the refactor.
- The **favorites heart** state (`inCart`) and its toggle keep working, and remain hidden from guests.
- The **client activity beacons** — search events and catalog-session duration — keep firing, and remain fire-and-forget.
- Filters stay reflected in the **URL** so a filtered view is shareable and survives a refresh; brand change still resets the model filter.

## S21 — Settings: disabled products, families & brands *(contract → backend → frontend)*

Disabled entities are currently unreachable: every list endpoint returns enabled rows only, so once a product, family or brand is disabled there is no way back through the UI.

- **Backend:** expose the disabled rows for products, families and brands. The recommended shape is an **enabled-status filter on the existing admin list endpoints** rather than three new routes — one code path, one set of DTOs, one place to keep permissions right. See decision **Q3**; if the owner prefers dedicated endpoints, the plan follows that instead. Either way the filter or route is **admin-only** and the values come from a contract enum, not a raw boolean string.
- **Contract:** the query parameter or route constants, plus any DTO change needed to carry the disabled state.
- **Frontend:** a new **Settings tab** listing disabled products, families and brands — three sections or a segmented view, each with the entity's identifying fields and a **re-enable action**. After re-enabling, the row leaves the list and the corresponding catalog caches are invalidated so the entity reappears in the pickers and the storefront immediately.
- **Cascade rule:** re-enabling a product whose family or brand is still disabled, or a family whose parent is disabled, leaves the product effectively invisible. The plan must implement the rule chosen in decision **Q5** and surface it in the UI rather than letting the user re-enable something that stays hidden with no explanation.

# Open decisions — resolve with the owner before planning the marked sets

**Q1 (S19) — Letter extraction edge cases.** What happens when a family or brand name has fewer than two letters ("LG" is fine, "K" is not), starts with a digit, or contains accents or Arabic characters? Proposal: strip diacritics, keep Latin letters and digits only, uppercase, and right-pad with `X` when fewer than two characters remain — so "K" becomes `KX`. Confirm or replace.

**Q2 (S19) — Collision retry bound.** How many regeneration attempts before giving up? Proposal: **10 attempts**, then a 409 telling the user to enter a barcode manually. Note that five digits give 100 000 combinations per family–brand pair, so exhaustion is effectively impossible; the bound exists only to guarantee the loop terminates.

**Q3 (S21) — Filter parameter or new endpoints.** You asked for new APIs to fetch disabled rows. A **status filter on the existing admin list endpoints** is the smaller and more maintainable change — same DTOs, same permissions, no duplicated pagination logic. Dedicated endpoints are also fine and slightly more explicit. Which do you want?

**Q4 (S19) — Label content.** Should a printed label show only the barcode and its digits, or also the product name and price? This drives the label dimensions and how many fit on a page.

**Q5 (S21) — Cascade on re-enable.** When a product is re-enabled but its family or brand is still disabled, should the system (a) block the action and explain what must be re-enabled first, (b) allow it and warn that the product stays hidden, or (c) re-enable the family and brand automatically? Proposal: **(a)** — it is the only option that cannot leave the admin confused about why a re-enabled product never appears.
