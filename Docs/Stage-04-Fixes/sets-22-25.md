## S22 — Barcode label printing as PDF

Extends the product-page label printing built in S19 to supplier invoices, and moves both to server-side PDF.

### Supplier invoices — print all labels for a receipt

- Add a **print-barcodes action** to the supplier invoice, available on **every invoice regardless of status**.
- It opens a dialog listing the invoice's product lines with an **editable quantity per line, defaulting to that line's invoice quantity** — so a twelve-unit line of "display Samsung S20" and a ten-unit line of "battery Oppo F12" default to twelve and ten labels respectively.
- **Products with no barcode are skipped** — omitted from the dialog list, with a short note stating how many lines were skipped and why, so the absence is never silent.
- Confirming produces a **PDF** containing the requested number of labels per product, in line order.

### Product page — switch to PDF

- The existing per-product label printing (S19) currently renders through the browser print view. **Move it to the same server-side PDF pipeline**, so both entry points produce identical labels. The dialog keeps its current shape: a quantity input defaulting to the product's stock quantity.

### Generation

- **Server-side**, reusing the existing invoice-PDF infrastructure. The plan must identify that infrastructure and follow it rather than introducing a second PDF stack.
- **Symbology: Code 128** — the barcode format is nine alphanumeric characters, so EAN-13 and UPC cannot encode it. Name the library used and state whether it is already a dependency.
- Labels tile across the page in a grid sized so a standard label sheet is usable; the plan fixes the dimensions and states them.
- Label content follows what S19 established — keep the two entry points identical.
- Both endpoints are **admin-only** (and staff where the corresponding page is staff-visible — check the S18 parity work before deciding).

## S23 — Audit: `avgStockPrice` maintenance *(audit set — report and stop)*

### The suspected defect

`avgStockPrice` is currently recomputed **only on IN movements**. Under classic weighted-average costing that would be correct — an OUT removes quantity and value at the same average, leaving it unchanged. **But this app costs at FIFO**: an OUT consumes specific layers whose cost may be above or below the average, so the true average cost of the *remaining* layers does change. The stored figure therefore drifts from reality, and because stock valuation reads it, **stock valuation diverges from the actual FIFO value of remaining stock**, with the gap widening at every OUT.

### The corrected rule (owner-approved — audit against this)

```
newAvgStockPrice = (oldAvgStockPrice × quantityOnHandBefore − movement.costOfGoods) ÷ quantityOnHandAfter
```

- The subtracted term is the movement's **total `costOfGoods`**, not a single layer's cost — one OUT can span several layers, and `costOfGoods` (already stored on the OUT row, itemised in the consumption rows) is the exact sum consumed.
- **The quantity is `quantityOnHand`**, never `onHand − reserved`: layers are physical. **`PENDING_ORDER`, `PENDING_REPAIR` and `PENDING_RELEASE` must not touch the average at all** — a reservation moves no layers.
- **When `quantityOnHandAfter` is zero, keep the last average** rather than dividing by zero or resetting. It keeps margin displays and repricing defaults meaningful for a temporarily out-of-stock product, and the next IN overwrites it.
- The rule is equivalent to `Σ(remaining layer qty × layer cost) ÷ Σ(remaining qty)`; the plan may verify against that identity.

### Audit scope

Examine **every** movement type for its effect on `avgStockPrice`:

- **IN** — `SUPPLIER_INVOICE`, `INITIAL_STOCK`, `ADJUSTMENT_IN`, `RETURN_IN`. Confirm the existing weighted recompute is right for each, and note that `RETURN_IN` re-enters at the **consumed** cost, not the current average.
- **OUT** — `SALE`, `ORDER_OUT`, `REPAIR_CONSUMPTION`, `ADJUSTMENT_OUT`. All four now require the recompute above. `ADJUSTMENT_OUT` has no revenue but does have a `costOfGoods`.
- **PENDING** — confirm none of the three touches the average.
- Confirm every recompute happens **inside the owning transaction on a locked row**, never in a listener.
- Confirm **`avgPrice` is untouched by this set** — it is maintained only from supplier invoices and must stay that way.
- Identify every **consumer** of `avgStockPrice` (margin displays, adjustment defaults, stock valuation in statistics, the supplier-invoice reprice section, product info) and note which figures will shift once the rule is corrected.

### Output

Write `Docs/Stage-04-Fixes/results/findings-S23-avg-stock-price.md` and **stop**. For each finding: severity, the file and function, a **worked numeric example** demonstrating the error (e.g. two layers at different costs, an OUT crossing both, the stored average versus the true one), and a proposed fix. Do not change code. The owner decides, and the fix plan is written afterwards.

**No data backfill.** Existing averages are wrong on test data and stay wrong; the corrected rule applies from the next movement.

## S24 — Audit: statistics correctness *(audit set — report and stop; needs S23)*

A full statistics audit ran earlier in the programme, but the semantics have moved since — orders and repairs both changed when they recognise revenue, repairs stopped producing sale records, and the payment ledger became the source of truth for `totalPaid`. This audit is a **second pass against current semantics**, not a repeat.

### What to verify

- **Product cost and profit.** Every figure must come from the **stored** per-line `costOfGoods` and `profit`, never recomputed from today's average. Confirm no report re-derives cost from `avgStockPrice`.
- **Revenue recognition timing.** Orders count **only at `COMPLETED`**; nothing accrues while confirmed, packaged or in delivery. Repairs count **only at `PICKED_UP`**. Verify no report counts an order at confirmation or a repair at completion.
- **Repairs as a revenue source.** Repairs no longer produce sale records, so repair revenue no longer arrives through sales figures. Verify it is read **directly from repairs**, appears exactly once, and is neither lost nor double-counted alongside repair invoices.
- **Payments.** `totalPaid` comes from the client-payment ledger; refunds are negative-amount rows. Verify payment totals sum the ledger (so refunds reduce them naturally) rather than reading document-level `paidAmount`, and that walk-in payments — which have no ledger row — are handled deliberately, not dropped silently.
- **Invoices.** Invoice-derived figures must agree with their source documents. Check that `REPAIR`-source invoices are included where they belong, and that no report both counts a repair and its invoice.
- **Stock in and out.** Movement-summary figures must reconcile with the ledger per type, and reservations must never appear as stock movement in or out.
- **Returns.** Verify returned quantities and amounts reduce revenue and profit correctly, that a partial versus a full return behaves per the recorded rules, and that restocked returns re-enter at the consumed cost in valuation terms.
- **Stock valuation** uses `avgStockPrice` — flag any interaction with S23's findings.
- **Credit and ageing.** Client and supplier credit totals must reconcile with their ledgers.
- Check the **frontend** too: a correct backend figure mislabelled, misaggregated or filtered differently in the UI is the same defect to the owner.

### Output

Write `Docs/Stage-04-Fixes/results/findings-S24-statistics.md` and **stop**. For each finding: severity, the report or endpoint affected, the file and function, a **worked example** showing the wrong figure versus the right one, and a proposed fix. Separate **unambiguous bugs** from **semantic questions needing the owner's decision** — do not resolve the latter yourself. Do not change code; the fix plan follows the owner's decisions.

## S25 — Receipt printing & document exports

### POS receipt — 80mm thermal

- Reformat the POS receipt for an **80mm** roll: narrow single-column layout, monospace-friendly, no wide tables, print stylesheet sized to the roll with no page margins fighting the printer.
- Printing stays a **browser print view** (not a PDF) — it is faster at the counter and matches the current button.
- The receipt carries the **store header from settings** (name, address, phone, logo where the format allows).
- **No barcode** of the sale reference.
- Keep every figure the receipt shows today: lines, total, previous credit, grand total, total paid, new credit.

### CSV exports — audit and fix

Review the existing CSV exports for **delivery fees** and the **movement ledger**: correctness and completeness of columns, separator and quoting/escaping (fields containing commas, quotes or newlines), encoding and BOM so accented and Arabic text opens correctly in Excel, date and decimal formatting, and whether the export respects the **currently active filters**. Fix what is wrong; **CSV stays alongside the new PDF**, it is not replaced.

### PDF exports — add

Add a **PDF download** beside the CSV for: **delivery fees**, the **movement ledger**, **stock levels**, and the **statistics reports**.

- **Server-side**, reusing the same PDF infrastructure as invoices and S22's labels — one stack, not three.
- Each export **respects the currently active filters** and contains the **complete filtered result set, unpaginated** — never just the page on screen.
- Landscape where the column count needs it, repeated header row across pages, page numbers, a title block naming the export, the filters applied and the generation timestamp.
- Statistics reports include their **chart** where one exists, plus the table.
- The plan must state how a very large export is handled (streaming, a timeout, or a row ceiling with a clear message) — an unbounded ledger export must not hang the request.
