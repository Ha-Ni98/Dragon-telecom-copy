# Dragon Telecom — Fix Programme: Sets S26–S29

**Standing context:** the app and database are **not in production** — the data is test data only. Schemas may change and migrations be created freely, but **no data backfill or repair script is wanted**; corrected logic applies going forward.

# THE SETS

**Order:** S26 → S27 → S28 → S29. S27 consumes settings fields and the print logo introduced in S26. S28 and S29 are independent.

## S26 — Image pipeline, R2 storage & logo/header settings

### Upload pipeline (backend)

Every image upload in the app goes through **one** pipeline — product images, brand logos, family icons, the store logo and the store print logo. Build it once as a shared service; do not duplicate it per module.

1. **Validate by content, not extension** — sniff the type from the file's magic bytes. Accept JPEG, PNG, WebP and HEIC; reject everything else with a clear error. Cap the raw upload at **10MB**.
2. **Process with `sharp`:** auto-rotate from EXIF orientation (phone photos arrive sideways), **strip all metadata** (removes GPS data and noticeable weight), and set **`limitInputPixels`** — without it a crafted 50,000×50,000 PNG decompresses into gigabytes and kills a 1GB machine.
3. **Resize** so the long edge is at most **1600px** for the main image, never upscaling a smaller original.
4. **Encode WebP at quality 85** — visually lossless for product photography at this size; expect a 3MB phone photo to land around 50–120KB.
5. **Emit a 400px thumbnail** for grids and POS product cards, so list views don't pull full-size images.
6. **Content-addressed keys** — name the object from a hash of the processed bytes. Deduplication and cache-busting both come free.

**Exception — the print logo** (see below) is stored as **PNG with no lossy encoding**, capped at 600px wide. Lossy compression of a black-and-white image produces edge artifacts that a thermal head renders as grey fringing.

### Storage (Cloudflare R2)

- Upload via the **S3-compatible SDK**; account id, bucket, access keys and the public base URL come from environment variables, validated at boot alongside the existing env schema.
- Serve through a **custom domain / public bucket URL** so image traffic never passes through the Fly machine — it keeps egress off the app's bandwidth and off its memory.
- Set `Cache-Control: public, max-age=31536000, immutable` — safe because keys are content-addressed.
- **Deletion removes every derivative** (full size and thumbnail). The existing product-image removal feature must be checked for orphans.
- The plan must state what happens when R2 is unreachable: the upload fails cleanly with a surfaced error, and no database row is written pointing at an object that doesn't exist.

## S27 — Thermal printing: 80mm receipt & barcode labels *(needs S26)*

### The POS receipt

The current output is wrong both physically and in content. It prints as a narrow block on a full-width sheet — `@page` is still defaulting to A4/Letter and the content carries an inherited max-width — and it renders faint, because thermal heads reproduce thin or grey text poorly.

**Physical:**
- `@page { size: 80mm auto; margin: 0 }` with `html, body { width: 80mm }`; treat **~72mm as the printable width** and keep all content inside it.
- **Bold monospace** face, pure `#000`, no greys, no shadows, no borders lighter than 1px solid black, no background fills.
- Height is content-driven (`auto`) — the roll cuts at the end, so nothing should force a page break.
- Printing stays a **browser print view**, not a PDF.

**Structure**, top to bottom — every label follows the app's EN/FR setting like the rest of the UI:

1. **Print logo** from settings (S26), centered, monochrome.
2. **Store block:** name, activity line, address, then the two labelled phone numbers (repair / sales).
3. **Separator** (dashed rule, full width — use a repeated character or a 1px solid black border).
4. **Items table** with column headers for label, quantity, unit price and line total. The product label **wraps onto as many lines as it needs**; quantity, unit price and total stay right-aligned on the first line of the row. This is the single most important difference from the current output, where a long product name is simply cut.
5. **Item summary:** number of distinct articles and total quantity.
6. **Money block:** total, discount, amount payable.
7. **Credit block** — previous credit, purchase total, amount paid, new credit — rendered **only when a POS client is attached**; a walk-in sale hides the block entirely rather than printing zeroes.
8. **Client name**, when attached.
9. **Footer:** the sale reference, date and time, and the **cashier's name** (the sale's staff member). **No barcode.**

The figures all exist on the sale already: purchase total is the sale total, amount paid is `paidAmount`, previous and new credit are the stored snapshots, and the discount is the column kept at 0.

### Barcode labels — print dialog, not PDF

Both label entry points (the products page and the supplier-invoice page) currently generate a PDF the user must save and reopen. **Replace this with the same browser print path as the receipt**, so the print dialog appears directly and the label printer can be selected.

- Render labels as **HTML with a print stylesheet**; drop the server-side PDF generation for labels entirely. **Remove the PDF download from both pages** — it is not kept as a secondary action.
- Add a **label size field to the print dialog**, alongside the existing quantity inputs: a set of common presets (for example 40×30mm, 50×25mm, 50×30mm) plus a **custom width × height** option. The chosen size drives `@page { size: <w>mm <h>mm; margin: 0 }` exactly — a mismatch here is what makes a label printer misfeed. Remember the last chosen size so the counter isn't re-picking it every time.
- **One label per page**, since label stock is a continuous roll of discrete labels.
- Label content stays as established: the **Code 128** symbol plus its human-readable value. Size the symbol to the chosen label, leaving a quiet zone on both sides — a barcode printed edge to edge won't scan.
- Everything else already agreed stays: supplier invoices offer this on **any invoice**, quantities default to each line's invoice quantity and are editable, and **products without a barcode are skipped with a visible count** explaining the omission.

## S28 — Inventory: pagination, per-product adjustment & PDF wrapping

### Stock levels

- **Paginate at 20 per page**, server-side, following the pagination pattern the other admin tables already use (`PaginationInfo`, the shared table shell, query-key composition). The filters and the barcode/name search added earlier must keep working across pages.
- Add an **Adjust action column**. Its button opens a **dialog** — it must not navigate to the Adjustments tab.
- The dialog carries the **same functionality as the Adjustments tab, scoped to the selected product**: reason select, optional note, counted quantity with a live delta preview, and on a **positive delta** a unit-cost field defaulting to the product's `avgStockPrice` with the helper text beneath it, plus the optional reprice sub-form prefilled with current prices.
- Submitting creates a normal adjustment document with a single line — same endpoint, same reference sequence, same movement types as the tab. Nothing about the adjustment model changes.
- On success, invalidate the stock levels, movement ledger and product caches so the row's quantity and average update immediately.

### Adjustments tab — product search

The product picker currently only offers the **most recent 20 products**, so anything older is unreachable. Make it **search the whole catalog server-side by name or barcode**, following the search pattern used by the POS product search, with debounce and pagination or a sensible result cap.

### PDF exports — text wrapping

The inventory PDF exports collapse and overlap their text: long product names and movement type names run over neighbouring columns and headers are cut mid-word.

- **Cell text wraps onto additional lines** and the row height grows to fit — no clipping, no overlap, no mid-word truncation.
- Column widths are sized so the wide columns (product, type, reference, staff) get the room they need; use landscape where the column count demands it.
- The header row repeats on every page, and page numbers, the title block, the applied filters and the generation timestamp stay as they are.
- Apply the same treatment to **every** export built in S25 — stock levels, movement ledger, delivery fees and the statistics reports — since they share the generation code and the same defect.

## S29 — POS workspace layout & repair device label

### POS layout

The page currently scrolls horizontally: the cart panel is cut off at the right edge because the layout is wider than the viewport. The cause is a flex/grid child without `min-width: 0`, which lets long product names force the container wider instead of shrinking.

- Set **`minmax(0, 1fr)`** (or `min-width: 0`) on the layout children so they can shrink, and confirm the horizontal scrollbar disappears at common widths.
- **Truncate long product names to one line with an ellipsis**, with the full name in a tooltip. Names like "AFFICHEUR ACE BUZZ 6 PRIME • BUZZ 7 LITE • BUZZ 7 PRIME • BUZZ 7 PRIM…" can never fit, and wrapping them to three lines would destroy the card rhythm and the scan-and-tap rhythm of the list.
- Move the **sidebar flush to the left** with a small margin, reclaiming the wasted gutter.
- **Rebalance the two panes** toward the ticket, which holds editable quantity and price inputs and needs the room more than the product list does.
- Keep the four-price line on the product card readable at the narrower width — it is secondary information and may shrink or elide before the name does.

**Focus mode** — a toggle in the POS header that hides the sidebar and the top header and expands the workspace edge to edge. Exit via a floating button at the top right, the **Esc** key, or the same toggle. Remember the preference so the counter stays in focus mode across sessions. **Do not use the browser Fullscreen API** — it interferes with barcode scanners and print dialogs; a CSS-level layout toggle behaves predictably with both.

### Repairs — device label

The repair intake dialog has no device label field, although **`Repair.deviceLabel` already exists** in the schema as the free-text fallback for devices not in the catalog.

- Add the field to the dialog, **prefilled with the selected brand and model** (for example "Samsung S24 Ultra") and **freely editable** — the technician can correct or extend it.
- Recompute the default when brand or model changes, **unless the user has already edited the field manually** — an edited label must never be silently overwritten.
- When no brand or model is selected, the field stays empty and editable, preserving its existing role as the fallback for unlisted devices.
- The value persists to the existing column; no schema change is needed. Confirm the label renders on the repair detail view and the claim slip.
