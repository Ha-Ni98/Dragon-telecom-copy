# THE SETS

**Order:** S37 → S38 → S39. S39 consumes a setting introduced in S38, and both consume S37's token and formatter.

---

## S37 — Accent token system, price format & navigation

### The accent token (every page in the app)

The palette stays blue and white — roughly 60/30 — with the accent at about 10%. The accent is **scarlet in light mode and vermilion in dark mode**.

**Do not overwrite `--accent`.** shadcn already uses that token for subtle hover backgrounds, and redefining it would repaint every hover state in the app red. Add a new token:

```css
:root { --highlight: 358 75% 51%; --highlight-foreground: 0 0% 100%; }
.dark  { --highlight: 11 100% 61%; --highlight-foreground: 222 30% 6%; }
```

Expose it through the Tailwind config so `bg-highlight`, `text-highlight`, `border-highlight` and `ring-highlight` all work, then use those utilities rather than raw hex anywhere.

**Contrast note that changes the markup:** light scarlet carries white text at 4.7:1 (passes AA). Dark vermilion against white text is only **3.1:1 — it fails**. Any filled highlight surface in dark mode must use `--highlight-foreground` (near-black), which is why the token pair exists. A component that hardcodes white text on a highlight background will be unreadable in dark mode.

**Where the accent is used — storefront and client pages:** badges, the cart count bubble, the active nav underline, a small marker before section titles, hero slider dots, and hover rings on tiles and cards.

**Where it is used — admin and staff:** only the **active nav indicator, section-title markers, hover rings and the theme toggle**. **Status badges keep their semantic colors** (green, amber, grey, and red reserved for errors and destructive states). Red already means "error" in those tables; if promo-style badges and *cancelled* badges share one red, the tables stop communicating. This restriction is deliberate — state it in the plan so it isn't "unified" later.

**Where it is never used, anywhere:** primary buttons (those stay blue), large background fills, and long passages of text.

Also in this pass: replace the **cyan theme-toggle state** with the highlight token, and make sure **every error message carries an icon alongside its text**, so a red badge is never mistaken for a warning.

### Price format

Money on the **storefront and all client-facing pages** renders as **`3 200 DA`** — a space as the thousands separator, `DA` as the suffix. One shared formatter function; no inline `toLocaleString` or string concatenation at call sites.

**Scope is storefront and client pages only.** Admin, staff, POS, the 80mm receipt, invoices and the PDF exports **keep their current format** and are not touched by this set.

### Default language

**French becomes the default locale**, with English second. No Arabic, no RTL scaffolding.

### Header and navigation

**Desktop:** logo, a wide search bar, the language switch, the account control, and the cart with its count bubble in the accent color. Below the header, a **category bar** listing the top-level families, each opening a **hover dropdown of its child families**.

**Mobile:** logo and icons on the first row, a **full-width search bar** on the second. **No horizontal overflow at any phone width** — audit the whole storefront for the cause, which is typically a flex or grid child missing `min-width: 0` that lets long content force the container wider than the viewport.

**Mobile bottom navigation:** a fixed bar with **Home, Categories, Search, Cart, Account**. The active item carries the accent underline. **Categories opens the catalog with the family filter**, not a new page. Make sure the bar doesn't cover page content or sit above modals and drawers, and that it respects the device's safe area inset.

## S38 — Hero slider & storefront settings

### The hero slider

A new entity, managed by the admin.

**Model** — one row per slide:
- `desktopImageUrl` and `mobileImageUrl` — **two separate uploads**, so a wide banner isn't squeezed into a phone. Target roughly **1920×600 desktop** and **1080×1080 mobile**; state the exact guidance in the upload UI.
- **Text as a JSON column keyed by locale**, holding the title and the call-to-action label for `fr` and `en`. The text is **real text rendered over the image**, never baked into the picture — that's what makes it translatable, selectable, searchable and sharp on every display.
- `link` — where the slide's button goes.
- `isActive`, plus optional `startsAt` / `endsAt` for scheduling.
- `displayOrder`.

**No subtitle line.** Title and button only.

**Management** lives in **Settings → storefront**: upload both images, enter the two locales' text, set the link, toggle active, set the window, and reorder the slides. Images go through the **existing S26 pipeline** — do not add a second upload path.

**Frontend behavior:** 3–5 slides, **5 second autoplay**, swipe on touch, and **lazy loading for every slide after the first** so the first paint isn't waiting on images it won't show. Slider dots use the accent token from S37. The hero occupies about **40–50% of viewport height** so products are visible on the first screen — the audit's main complaint about the reference site is that the hero pushed everything below the fold.

**One slide should promote the repairer / professional account.** That is a call to action pointing at the existing client registration — there is no separate account type, and the client categories already carry the wholesale pricing idea. Seed or document it as an example slide rather than hardcoding it.

Respect the active flag and the schedule window on the public endpoint, ordered by `displayOrder`.

### Storefront settings additions

Add to **Settings → storefront**:
- **Repair-tools family** — a picker letting the admin choose which family feeds the "Repair tools" row on the home page (S39). Not a new flag on products; just a stored family id.
- **WhatsApp number** — alongside the existing store phone fields.
- **Meta description** and **link-preview image** for the site.

### Footer and page metadata

The footer currently uses **front-end static constants** for contact details. **Switch it to read from settings** — store name, address, the repair and sales phones, and the new WhatsApp number — so there is one source of truth and the owner can change them without a deploy. This deliberately reverses the earlier "footer is static" decision; say so in the plan.

Wire the **meta description and link-preview image** into the document head, with sensible fallbacks when the settings are empty.

Make the phone and WhatsApp numbers **tappable** — `tel:` and a WhatsApp deep link — on mobile and desktop alike.

## S39 — Tiles, home content & product cards

### Transparent assets sit on light tiles — in both themes

Brand logos and family icons are transparent PNGs, and most are dark. A dark logo on a dark tile is invisible, which is why the audit proposed per-brand overrides. **We are not adding those.** Instead:

**Every transparent asset sits on a white or near-white tile in both light and dark mode** — brand tiles, family icons, the **store logo in the header and footer**, and the inner image box on product cards. No logo can ever disappear, a newly added brand can't break, and there is **no new column on `Brand` or `Family` and no admin control to maintain**.

In dark mode this produces a row of light tiles. That is intentional and consistent — the same treatment product photos get — so it reads as a design decision rather than an oversight.

**Verify the upload pipeline preserves alpha.** S26 converts uploads to WebP, which supports transparency, but if the current settings **flatten onto a background** then every logo already carries a baked-in white rectangle that no amount of CSS can fix. Check this before styling anything; if it flattens, fixing the encoder is the first action in the plan.

**Upload guidance** for logos and icons, surfaced in the admin UI: square, at least 512px, trimmed of empty space, with roughly 10% internal padding so tiles look even.

### Categories and brands

- **Categories (families):** a horizontally scrolling row on mobile, a full row on desktop.
- **Brands:** a **grid showing every brand** — about 4 per row on mobile, 7–8 on desktop. **Drop the carousel**; a grid shows the whole range at a glance, and a shopper looking for their phone's brand shouldn't have to page through.

### Home page rows

Each section is its **own horizontally scrolling row**:

| Row | Source |
|---|---|
| **Featured products** | the existing settings-driven featured-products selection |
| **New arrivals** | products by `createdAt` descending, **capped at 3 per family** so one big delivery can't fill the row |
| **Repair tools** | products in the family chosen in Settings → storefront (S38) |

**Remove the search, filter and view-toggle bar from the home page** — the catalog is where filtering belongs, and that bar competes with the hero and the category row for the first screen.

### Product cards

- Product names in **normal capitalization, not ALL CAPS**, clamped to **2 lines** with the full name available on hover or long-press.
- The **price is the visually dominant element**, in the single `3 200 DA` format from S37.
- Badges use the accent token.
- **About 2.3 cards per row on mobile** — the partial third card is what tells a thumb the row scrolls.
- A **white inner box behind the image**, matching the tile rule above, so photos with transparent or light backgrounds stay consistent in dark mode.

Price visibility rules are unchanged: a guest sees the guest price or the "registered users only" state, an approved client sees his category price, and price resolution stays server-side.
